# 포트폴리오 리스크 사이징 — 포트폴리오 백테스트 엔진 설계안

상태: **초안 (승인 대기)** · 작성 2026-10-31 · 체크리스트: `docs/01-plan/features/portfolio-risk-sizing.checklist.md`

## 1. 목적

새 자금 운용 구조(풀 공유 + 1% 리스크 사이징 + 한도)가 **지금 구조(스윙별 배정금)보다 나은지** 같은 데이터·같은 신호로 비교한다.
수익 우위가 확인되기 전에는 실전 코드(중앙 조정기, 파킹 ETF)를 만들지 않는다.

## 2. 핵심 아이디어: 거래 기록 추출 → 날짜순 재생

단일 이평선 백테스트(`SingleEMABacktestStrategy.compute`)에서 **진입 신호·청산선·부분익절·쿨다운은 자본과 무관**하다. 자본에 의존하는 건 수량뿐이다.

1. **추출**: 종목마다 전략을 한 번 돌려 "단위 수량 기준 거래 기록"을 얻는다.
2. **재생**: 포트폴리오 엔진이 전 종목 거래 기록을 날짜순으로 재생하며 사이징·한도·우선순위를 적용한다.

신호를 다시 계산하지 않으므로 한도·우선순위 수치를 바꿔가며 수백 번 실험해도 빠르다.

### 한계 (결과 해석 시 감안)

- 한도에 걸려 **건너뛴 진입은 그대로 사라진다.** 실전에서는 신호 조건이 유지되면 자리가 난 뒤 다시 진입할 수 있다. 재생 방식은 이 늦은 진입을 재현하지 못한다. 한도가 빡빡할수록 수익을 **과소 평가**하는 쪽의 편향이다.
- 진입이 한 번 일어난 종목의 이후 경로는 "진입했다"는 가정 하에서만 만들어진다 (쿨다운 상태 포함).
- 일봉 기반이라 장중 순서를 모른다. 같은 날 청산과 진입이 겹치면 **청산 먼저**로 처리한다 (파킹 ETF를 팔고 즉시 재매수가 된다는 가정과 같다. 스위치로 반대도 실험).
- 실거래의 실시간 accum은 재현 불가 (알고 수용한 한계, 체크리스트 1단계 참조).

## 4. 입력·출력 형식

### 4.1 단위 거래 기록 (추출 결과, 종목·사이클 단위)

```
UnitTrade:
  market: "KR" | "US"        code: str
  entry_date, entry_price    # 슬리피지 반영 체결가 (기존 fill_buy)
  initial_stop               # 진입 시 청산선 = 1R 기준 (R = entry_price − initial_stop)
  conviction                 # 우선순위 기준
  exit_line_by_date          # 보유 중 일별 청산선 (열린 리스크 계산용)
  events: [(date, kind, price, qty_ratio)]   # kind: PARTIAL | EXIT | FINAL_LIQUIDATION
```

수량은 `unit_qty`(예: 10,000주)로 고정해 돌리고, 재생 때 `실제수량 / unit_qty`를 곱해 환산한다 (수수료·세금은 금액에 비례하므로 재계산).

### 4.2 엔진 파라미터

```
mode            "pool"(풀 공유·리스크 사이징) | "fixed_alloc"(현재 구조 재현: 종목별 배정금)
equity0         시장별 초기 총자산
risk_pct        0.01
max_position_pct  종목당 최대 금액 / 총자산
max_positions   동시 보유 상한 (None = 제한 없음)
max_open_risk_pct  총 열린 리스크 상한 (None = 제한 없음)
priority        "conviction" | "narrow_stop" | "random"(대조군, seed)
exits_first     True (같은 날 청산 후 진입)
adv_ratio       0.05 (일평균 거래대금 대비, 재생 시 적용)
park_apy        0.0 | 시장별 파킹 수익률 (현금에 일할 가산)
```

### 4.3 출력

시장별(KR, US 분리 — 통화·자금 분리) 지표: CAGR, MDD, MAR, 샤프, 소르티노, **평균 현금 비중**, 평균·최대 동시 보유, 총 열린 리스크 최대, 거래 수, 평균 R, **한도로 건너뛴 신호 수(사유별)**, 단순 보유·지수 대비.

## 5. 재생 알고리즘 (하루 단위)

```
for date in 거래일:
    1. 파킹 수익 가산 (park_apy > 0 이면 현금에 일할)
    2. 오늘 발생한 청산/부분익절 처리 → 현금 가산 (비용 반영)
    3. 오늘 진입 후보를 priority 순으로 정렬
       for 후보:
          qty = risk_sizing.calc_qty(equity, risk_pct, entry, initial_stop, max_position_pct)
          한도 검사: 현금 >= 금액, 보유 수 < max_positions,
                    열린 리스크 + 이 포지션 리스크 <= max_open_risk, 유동성(adv) 통과
          통과 → 매수 (비용 반영), 불통과 → 사유 기록 후 건너뜀
    4. 종가로 평가 → equity 기록, 열린 리스크 갱신 (포지션별 max(0, (진입가 − 현재 청산선)) × 수량)
```

- `equity` = 현금 + Σ(수량 × 종가). 사이징 기준은 **전일 종가 평가 총자산**.
- 미국은 환전 비용(매수·매도 각 0.25%)을 체결마다 반영 (기존 시뮬레이터와 동일).
- 구간 마지막 날 미청산 포지션은 종가 평가로 정리 (기존 `_liquidate_final_position`과 같은 규칙).

## 6. 실험 계획

기간은 기존 계획서 규칙을 따른다: 개발 2020-05-01~2026-10-23, 홀드아웃 2015-01-01~2019-12-31 (**최종 후보 1회만**).

| ID | 내용 | 보려는 것 |
|---|---|---|
| E0 | `fixed_alloc` 재현 | 현재 구조의 성과·노출률 (기준선) |
| E1 | `pool`, 1%, 한도 느슨 | 풀 공유 효과 |
| E2 | 한도 격자: 종목 수 {5,10,20,30} × 종목당 상한 {10,20,30%} × 총 리스크 {4,8,12%} | 한도 수치별 수익·낙폭 |
| E3 | 우선순위: conviction / 좁은 손절 / 무작위(여러 시드) | 순위 기준이 의미 있는지 |
| E4 | 파킹 수익 0 vs 시장별 연 수익률 | 노는 돈 해소 효과 |
| E5 (2차) | 이익 구간 % 기준 vs R 기준 | 전략 변형 훅이 필요해 설계 후속 |

E2 격자에는 `risk_pct` {0.25%, 0.5%, 0.75%, 1%}를 포함한다. (구조 점검에서 확인: 1%와 평균 손절폭 5~6%에서는 포지션당 총자산의 16~20%가 들어가 현금이 먼저 바닥나고, 신호의 85~90%가 `cash`로 건너뛰어진다. 이 설정에서는 종목 수·총 리스크 한도가 거의 걸리지 않는다.)

### 판정 기준 (2026-10-31 확정 — 성과 수치를 보기 전에 고정. 구조 점검 때는 신호·체결·건너뜀 수만 봤다)

개발 구간에서 아래를 **국내(KR)와 미국(US) 모두** 만족하는 설정만 후보로 인정한다.

1. **MAR(CAGR ÷ MDD)이 E0(현재 구조)의 1.2배 이상**
2. **무작위 우선순위 대조군(시드 30개, 같은 설정)의 MAR 분포 상위 10%(90분위) 이상** — 신호 순위 기준이 아니라 우연으로 좋아 보이는 결과를 거른다
3. 후보가 여러 개면 위 조건을 통과한 것 중 **MAR이 높은 것을 고르되, 격자의 인접 설정에서도 조건 1이 유지될 때만** 인정한다 (한 점만 튀는 과적합 방지)

후보가 정해지면 **홀드아웃(2015~2019)에서 1회만** 같은 조건 1을 확인한다. 개발 구간 결과를 보고 기준을 바꾸지 않는다. 기준을 못 넘으면 풀 공유 구조를 실전에 넣지 않고 원인을 분석한다.

참고(해석 시 감안): 종목 풀이 현재 DB의 종목이라 생존편향이 있고, 개발 구간은 상승장 비중이 크며, 일봉 기반이라 장중 순서와 건너뛴 진입의 늦은 재진입은 재현하지 못한다.

## 8. 승인 필요 사항

- 순서 변경: 체크리스트의 3단계(수량 계산기)를 2단계(엔진)보다 **앞**으로 당긴다. 엔진이 같은 함수를 써야 하기 때문이다.
- 재생 방식의 한계(건너뛴 진입이 사라짐)를 수용하는지. 수용하지 않으려면 신호 생성을 단계별 이벤트 시뮬레이션으로 바꿔야 하고 작업량이 크게 늘어난다.
- E0(현재 구조 재현)를 같은 엔진으로 만드는 것 (비교 기준선).
