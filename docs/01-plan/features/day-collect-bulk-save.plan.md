## 1. 개요

### 1.1 목적

`day_collect_job` / `us_day_collect_job` 이 종목별 코루틴에게 **같은 AsyncSession** 을 넘겨
각자 `commit()` 하게 두는 구조를 걷어낸다. 저장 주체를 잡 1곳으로 모아
동시 트랜잭션 조작 자체를 불가능하게 만든다.

### 1.2 배경

`STOCK_DAY_HISTORY` 는 실시간 지표가 **전일 완성봉 기준**으로 참조하는 테이블이다.
수집이 일부 종목만 실패해도 그날 일봉이 비고, 다음 거래일 지표가 그대로 오염된다.
장애가 조용히 진행되는 경로라 우선순위가 높다.

## 2. 문제 정의

### 2.1 증상 A — 공유 세션 동시 commit 으로 저장 실패

운영 로그 (2026-09-18 06:40):

```
06:40:00.116  INSERT INTO STOCK_DAY_HISTORY ...        ← 079550 저장
06:40:00.118  200 OK (278470), 200 OK (267260)
06:40:00.119  [DAY COLLECT] 데이터 수집 실패 (278470):
              Method 'rollback()' can't be called here;
              method 'commit()' is already in progress
06:40:00.127  [DAY COLLECT] 데이터 수집 실패 (267260): (동일)
```

발생 경로:

| 단계 | 위치 | 내용 |
|------|------|------|
| 1 | `auto_swing_batch.py:863` | 잡이 `StockService(db)` **1개** 생성 |
| 2 | `auto_swing_batch.py:875-879` | 종목별 코루틴에 같은 인스턴스를 넘겨 `gather` |
| 3 | `auto_swing_batch.py:1003` | 각 코루틴이 `save_history_bulk` 호출 |
| 4 | `stock/service.py:54` | 각자 `await self.db.commit()` |

`_SEMAPHORE = asyncio.Semaphore(5)` (`auto_swing_batch.py:115`) 이고 대상 종목이 5개라 전부 동시에 진입한다.
`commit()` 은 MySQL 왕복에서 `await` 로 제어권을 놓고, 그 사이 다른 코루틴이 같은 세션의 트랜잭션 상태를 바꾸려다
`IllegalStateChangeError` 가 난다. 이 예외는 `SQLAlchemyError` 하위라 `stock/service.py:56` 의 `except` 에 잡히고,
핸들러의 `rollback()` 이 **같은 이유로 다시** 거부되면서 로그의 메시지가 밖으로 나온다.

### 2.2 증상 B — 5종목 쓰기가 한 트랜잭션에 섞임

세션이 하나라 트랜잭션도 하나다. 어느 코루틴의 `rollback()` 이 성공하면
**다른 종목이 방금 넣은 행까지 함께 사라진다.** 에러 로그 없이 데이터만 비는 경로다.

### 2.3 대조군 — 같은 파일의 다른 배치는 안전하다

| 배치 | 세션 소유 | 안전 여부 |
|------|-----------|-----------|
| `process_single_swing` | 코루틴마다 `Database.get_session()` (`auto_swing_batch.py:193`) | 안전 |
| `fetch_and_store_3_years_data` | 호출마다 자체 세션 (`stock_data_batch.py:89`) | 안전 |
| `collect_single_stock` | **잡의 세션을 공유** | **결함** |

즉 이 파일 안에 이미 올바른 패턴이 있고, 일별 수집 잡 두 개만 예외다.

## 3. 범위

### 3.1 포함

- [x] FR-01: `collect_single_stock` 이 저장하지 않고 행 dict 를 `return`
- [x] FR-02: 잡이 `gather` 결과를 모아 `save_history_bulk(rows)` **1회** 호출 (국내·미국 동일)
- [x] FR-03: 행 단위 필수 필드 검증 — 불량 행은 해당 종목만 제외 + warning
- [x] FR-04: 집계 로그를 수집 성공/실패와 **저장 건수**로 분리
- [x] FR-05: 회귀 테스트 — 공유 세션 동시 커밋 미발생, 불량 행 제외, 저장 1회 호출

FR-03 은 선택이 아니다. OHLCV 컬럼이 전부 `nullable=False` (`stock/entity.py:31-35`) 인데
현재는 `if response:` 만 보고 개별 필드를 확인하지 않는다. 지금은 불량 응답이 **그 종목만** 실패시키지만,
저장을 1회로 합치면 **그날 전체**가 롤백된다. 검증 없이 합치면 결함을 더 키우는 변경이 된다.

### 3.2 제외

- **`gather`·세마포어 제거**: 수집 잡은 `BATCH_USER_ID` 앱키 하나로 전 종목을 조회하므로,
  `1047295` 의 앱키 단위 레이트 리미터가 배포되면 어차피 직렬화된다(실전 10/s → 5종목 약 0.5초).
  병렬성의 실익은 거의 없지만 종목 수 증가에 대비해 구조는 남긴다. 이번 결함과 직교한다.
- **종목별 세션 분리안**: 동작은 하나 `DB_POOL_SIZE=10` 에서 종목 수만큼 커넥션을 점유한다.
  `process_single_swing` 이 세션을 나누는 이유는 스윙마다 읽기-수정-쓰기 트랜잭션이 독립이기 때문이고,
  "행 N개를 넣기만" 하는 수집 잡은 성격이 다르다.
- **`asyncio.Lock` 직렬화안**: 변경량은 가장 작지만 공유 세션이 남아, 이 세션을 쓰는 코드가
  하나만 더 생겨도 재발한다. 원인을 덮는 선택이다.
- **수집 대상 범위 조정** (`DATA_YN='Y'` 전체 → 활성 스윙): 별건.
- **유량 초과 타임아웃**: `1047295` 에서 해결됨. 배포만 남았다.
