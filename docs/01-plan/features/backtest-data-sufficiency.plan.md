# Plan: 백테스트 데이터 충분성 검증 (backtest-data-sufficiency)

> **요약**: 주가 데이터가 부족한 종목의 백테스트가 "정상 결과"처럼 응답되는 문제를 막는다.
> 0건만 걸러내는 현재 가드를 전략별 최소 요구 봉 수 기준으로 바꾼다.
>
> **작성일**: 2026-09-20
> **상태**: Draft
> **관련**: 데이터 적재는 활성화 시점 단일 트리거(`swing/service.py:159` `_ensure_stock_data`)

---

## 1. 개요

### 1.1 목적

백테스트가 **데이터 부족을 부족이라고 말하게** 한다.
자동 적재는 이번 범위가 아니다 (3.2 참고).

### 1.2 배경

데이터 적재는 스윙 **활성화(`USE_YN` N→Y)** 시점에만 일어난다.
등록/목록조회 시점에 적재하지 않는 이유는 `_ensure_stock_data` docstring 에 있다 —
활성화하지 않을 종목까지 3년치를 받고 `DATA_YN='Y'` 가 되면
`day_collect_job` 이 그 종목을 영구히 매일 수집하기 때문이다.

따라서 **아직 활성화하지 않은 종목은 `STOCK_DAY_HISTORY` 가 비어 있는 것이 정상**이고,
백테스트는 그 상태에서도 호출될 수 있다.

---

## 2. 문제 정의

### 2.1 증상 A — 부족한 데이터로 계산하고 정상 응답한다

```python
# backtest/backtest_service.py:77-79
price_days = await stock_service.get_stock_history(MRKT_CODE, ST_CODE, start_date)
if not price_days:
    raise ValidationError("주가 데이터가 없습니다.", field="ST_CODE")
```

**0건만** 막는다. 1건이라도 있으면 통과해 3년 백테스트를 수행한 것처럼 응답한다.
요청은 3년(`start_date`)·평가구간 2년(`eval_start`, `:71-73`)을 전제하는데,
실제로 몇 개의 봉으로 계산했는지는 응답 어디에도 없다.

### 2.2 증상 B — 지표가 조용히 무신호를 반환한다

전략별 최소 요구 봉 수:

| 전략 | 최장 지표 | 최소 필요 봉 | 부족 시 동작 |
|------|-----------|--------------|--------------|
| `S` 단일 20EMA | `ema_long=120` (`single_ema_backtest_strategy.py:149`) | 120+ | EMA 가 NaN → 진입 판정 불가 |
| `A` 3-EMA | `long_term` (기본 60, 요청값 가변) | 요청값+ | 동일 |
| `B` 일목균형표 | 선행스팬B 52 + 시프트 26 | **79** | **조용히 `False, False, False, False` 반환** |

특히 `B` 는 `tech_analysis.py:205-207` 에 이미 길이 가드가 있다:

```python
min_needed = max(SENKOU_B_PERIOD, KIJUN_PERIOD, TENKAN_PERIOD) + 26 + 1   # = 79
if len(df) < min_needed:
    return False, False, False, False
```

데이터가 79봉 미만이면 **매수·매도 신호가 전부 False** 가 되어
"거래 0건 / 수익률 0%" 라는 **그럴듯한 결과**가 나온다. 사용자는 이것을
"이 전략은 이 종목에서 거래가 없었다"로 읽는다. 실제로는 계산 자체가 불가능했던 것이다.

### 2.3 영향

백테스트는 전략·종목 선택의 근거다. 틀린 결과를 조용히 내놓는 것은
결과를 안 주는 것보다 나쁘다.

## 3. 범위

### 3.1 포함

- [ ] FR-01: 전략별 최소 요구 봉 수 산출 (최장 지표 기간 기반)
- [ ] FR-02: 조회 결과가 요구치 미만이면 `ValidationError` — **보유 구간과 필요 봉 수를 함께** 알린다
- [ ] FR-03: 평가구간(`eval_start` 이후) 봉 수도 검증 — 워밍업만 있고 평가할 구간이 없으면 결과가 무의미하다
- [ ] FR-04: 응답에 실제 사용한 데이터 구간(시작일·종료일·봉 수) 포함 — 3년치인지 아닌지 드러나게
- [ ] FR-05: 회귀 테스트 — 전략별 경계값(79/120), 평가구간 부족, 정상 케이스

### 3.2 제외

- **백테스트 시 자동 적재**: 별건으로 분리한다. 세 가지를 같이 풀어야 하기 때문이다 —
  ① 3년치는 KIS 다회 호출이라 동기 처리 시 응답이 수십 초 ②적재하면 `DATA_YN='Y'`
  (`stock_data_batch.py:198`)가 되어 백테스트만 해본 종목도 영구 수집 대상이 된다
  ③ `run_backtest(db, swing_data)` 가 `user_id` 를 받지 않아 라우터부터 배선 변경이 필요하다.
  이번 변경은 **부족을 정확히 알리는 것**까지다.
- **`DATA_YN` 상태 체계 개편**: 백테스트용 임시 적재를 `'Y'` 로 승격하지 않는 별도 상태가
  필요하지만, 수집 배치 대상 선정과 엮여 있어 독립 설계가 필요하다.
- **부족 시 부분 기간 백테스트 허용**: 지금은 금지한다. 허용하려면 결과에
  "이 구간만 검증됨"을 명시하는 UI 계약이 선행되어야 한다.

## 5. 리스크

| 리스크 | 완화 |

| 기존에 통과하던 요청이 422로 바뀐다 | 원래 신뢰할 수 없던 결과다. 메시지에 필요 봉 수·보유 구간을 담아 다음 행동(활성화 후 재시도)을 안내 |
